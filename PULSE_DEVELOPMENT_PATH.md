# Pulse — Structured Development Path

This is not a sprint plan. It is a learning path disguised as a build plan.
Every step is small enough to understand completely before moving to the next.
Nothing gets generated by AI. Everything gets typed, read and understood.

The rule: do not move to the next step until the current one works and you can
explain what it does and why.

---

## How to Use This Document

Each step has three parts:

**What you build** — the concrete thing to add or change.
**What you learn** — the concept behind it, not just the syntax.
**How you know it works** — a specific thing you can verify.

When you finish a step, close your editor and explain it out loud as if you are
in an interview. If you cannot explain it, you have not learned it yet. Go back.

---

## Phase 1 — PostgreSQL and the Database Layer (Days 2 to 5)

This is the most important phase. Take your time here. Every project you build
from now on will use these patterns.

### Step 1.1 — Add PostgreSQL to Docker Compose

Update your `docker-compose.yml`:

```yaml
services:
```

What you learn: why we use a volume (data persists when the container restarts),
what the POSTGRES environment variables do, why PostgreSQL runs as its own
service rather than being embedded in the backend.

How you know it works: run `docker compose up db`, then connect with a database
client like TablePlus or DBeaver using the credentials above. You should see
an empty database called `pulse`.

### Step 1.2 — Install SQLAlchemy and Alembic

```
pip install sqlalchemy alembic psycopg2-binary python-dotenv
```

Update `requirements.txt` with these packages.

What you learn: what psycopg2 is (the PostgreSQL driver — SQLAlchemy needs it
to actually talk to PostgreSQL), what python-dotenv is for.

### Step 1.3 — Create your database configuration

Create `backend/database.py`:

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, DeclarativeBase
import os

DATABASE_URL = os.getenv("DATABASE_URL", "postgresql://pulse:pulse@localhost:5432/pulse")

engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

class Base(DeclarativeBase):
    pass

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

What you learn: what an engine is (the connection to the database), what a
session is (a unit of work — like a transaction), what the yield in get_db
does and why it is a generator, what autocommit=False means.

How you know it works: import this in main.py and print the engine. No errors.

### Step 1.4 — Write your first model

Create `backend/models.py`:

```python
from sqlalchemy import Column, String, DateTime, Enum as SQLEnum
from sqlalchemy.dialects.postgresql import UUID
from database import Base
import uuid
import enum
from datetime import datetime

class JobStatus(str, enum.Enum):
    queued = "queued"
    processing = "processing"
    completed = "completed"
    failed = "failed"

class Job(Base):
    __tablename__ = "jobs"

    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    filename = Column(String, nullable=False)
    status = Column(SQLEnum(JobStatus), default=JobStatus.queued)
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)
```

What you learn: what a model is (a Python class that maps to a database table),
what each column type means, why we use UUID as a primary key instead of an
integer, what nullable=False enforces, what onupdate does.

How you know it works: import Job in main.py. No errors.

### Step 1.5 — Set up Alembic

```bash
cd backend

```

Edit `alembic.ini` — find the `sqlalchemy.url` line and change it to:
```

```

Edit `migrations/env.py` — import your Base and models:
```python

```


What you learn: what a migration is and why it matters, what autogenerate does

How you know it works: open your database client. The `jobs` table exists with
the correct columns.

### Step 1.6 — Write a job creation endpoint

Update `backend/main.py`:

```python
from fastapi import FastAPI, Depends
from sqlalchemy.orm import Session
from database import get_db
from models import Job
from pydantic import BaseModel

app = FastAPI()

class CreateJobRequest(BaseModel):
    filename: str

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/jobs")
def create_job(request: CreateJobRequest, db: Session = Depends(get_db)):
    job = Job(filename=request.filename)
    db.add(job)
    db.commit()
    db.refresh(job)
    return {"id": str(job.id), "filename": job.filename, "status": job.status}

@app.get("/jobs")
def list_jobs(db: Session = Depends(get_db)):
    jobs = db.query(Job).all()
    return [{"id": str(j.id), "filename": j.filename, "status": j.status} for j in jobs]
```

What you learn: how FastAPI dependency injection works (Depends), what db.add
and db.commit do, what db.refresh does and why it is needed, how Pydantic
validates request bodies.

How you know it works: POST to http://localhost:8000/jobs with a JSON body.
Check the database — the row is there. GET /jobs returns it.

### Step 1.7 — Add the database URL to Docker Compose

Update the backend service in docker-compose.yml:

```yaml
backend:
  environment:
    - DATABASE_URL=postgresql://pulse:pulse@db:5432/pulse
  depends_on:
    - db
```

What you learn: why the host is `db` not `localhost` inside Docker (service
names are DNS hostnames on the Docker network), what depends_on does and what
it does NOT do (it does not wait for the database to be ready — you need
retry logic for that, which comes in a later step).

How you know it works: `docker compose up` — the backend connects to PostgreSQL
and the health check passes.

## Phase 2 — Redis and the Queue (Days 6 to 9)

You now have a database. Jobs are created and stored. The next problem:
processing takes time and we do not want to block the HTTP request while it happens.

### Step 2.1 — Add Redis to Docker Compose

```yaml
redis:
  image: redis:7-alpine
  ports:
    - "6379:6379"
```

What you learn: why Redis uses alpine (smaller image), what port 6379 is,
why Redis does not need a volume by default (it is intentionally temporary).

How you know it works: `docker compose up redis`, then run `redis-cli ping`
and get `PONG`.

### Step 2.2 — Install ARQ and connect to Redis

```
pip install arq redis
```

Create `backend/worker.py`:

```python
import asyncio
from arq import create_pool
from arq.connections import RedisSettings

REDIS_SETTINGS = RedisSettings(host="localhost", port=6379)

async def process_document(ctx, job_id: str, filename: str):
    print(f"Processing job {job_id} for file {filename}")
    await asyncio.sleep(2)  # simulate work
    print(f"Job {job_id} complete")
    return {"status": "completed"}

class WorkerSettings:
    functions = [process_document]
    redis_settings = REDIS_SETTINGS
```

What you learn: what an async function is and why workers are async, what ctx
is (the worker context — it holds the Redis connection and other shared state),
what WorkerSettings.functions means (it registers which functions this worker
can handle).

How you know it works: run `arq worker.WorkerSettings` — the worker starts
and waits for jobs.

### Step 2.3 — Enqueue jobs from the API

Update the create_job endpoint to push work onto the queue:

```python
from arq import create_pool
from arq.connections import RedisSettings

@app.post("/jobs")
async def create_job(request: CreateJobRequest, db: Session = Depends(get_db)):
    job = Job(filename=request.filename)
    db.add(job)
    db.commit()
    db.refresh(job)

    redis = await create_pool(RedisSettings())
    await redis.enqueue_job("process_document", str(job.id), request.filename)

    return {"id": str(job.id), "filename": job.filename, "status": job.status}
```

What you learn: what enqueue_job does (it pushes a message onto a Redis list),
why the API returns immediately without waiting for the job to complete, the
difference between the job record in PostgreSQL (permanent state) and the
message in Redis (temporary work instruction).

How you know it works: POST a job. The API returns instantly. The worker
terminal shows the processing happening separately. Check the database — the
job exists with status "queued" (it does not update to completed yet — that
comes next).

### Step 2.4 — Update job status from the worker

Update `worker.py` to connect to PostgreSQL and update the job status:

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
import os

DATABASE_URL = os.getenv("DATABASE_URL", "postgresql://pulse:pulse@localhost:5432/pulse")
engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine)

async def process_document(ctx, job_id: str, filename: str):
    db = SessionLocal()
    try:
        job = db.query(Job).filter(Job.id == job_id).first()
        job.status = "processing"
        db.commit()

        await asyncio.sleep(3)  # simulate AI work

        job.status = "completed"
        db.commit()
    finally:
        db.close()
```

What you learn: why the worker has its own database session (it is a separate
process from the API), why the try/finally pattern matters here, what happens
if the worker crashes mid-job (the status stays as "processing" — this is the
problem that retry logic solves, coming soon).

How you know it works: submit a job, watch the status in the database change
from queued to processing to completed.

### Step 2.5 — Add retry logic

Update the worker function with error handling:

```python
async def process_document(ctx, job_id: str, filename: str):
    db = SessionLocal()
    try:
        job = db.query(Job).filter(Job.id == job_id).first()
        job.status = "processing"
        db.commit()

        # simulate a random failure
        import random
        if random.random() < 0.3:
            raise Exception("Simulated processing failure")

        await asyncio.sleep(3)
        job.status = "completed"
        db.commit()

    except Exception as e:
        job.status = "failed"
        db.commit()
        raise  # re-raise so ARQ knows to retry
    finally:
        db.close()
```

Add retry settings to WorkerSettings:

```python
class WorkerSettings:
    functions = [process_document]
    redis_settings = REDIS_SETTINGS
    max_jobs = 10
    job_timeout = 300
    retry_jobs = True
    max_tries = 3
```

What you learn: why you re-raise the exception (ARQ needs to know the job
failed to decide whether to retry), what max_tries controls, what job_timeout
means and why it matters for long-running AI tasks.

How you know it works: submit several jobs. About 30% fail on first attempt.
Watch ARQ retry them automatically. Check PostgreSQL for the final statuses.

## Phase 3 — WebSockets and Real-time (Days 10 to 13)

The queue works. Jobs process in the background. But the user still has to
refresh the page to see updates. This phase fixes that.

### Step 3.1 — Understand WebSockets first

Before writing any code, read the FastAPI WebSocket documentation:
https://fastapi.tiangolo.com/advanced/websockets/

Read it completely. Understand the connection lifecycle: connect, send, receive,
disconnect. Understand why WebSockets are different from HTTP.

Then answer these questions in writing before continuing:
- What is the difference between HTTP and WebSocket?
- Why would you use WebSocket instead of polling?
- What happens when a WebSocket connection drops?

### Step 3.2 — Create a connection manager

Create `backend/connection_manager.py`:

```python
from fastapi import WebSocket
from typing import dict

class ConnectionManager:
    def __init__(self):
        self.active_connections: dict[str, WebSocket] = {}

    async def connect(self, job_id: str, websocket: WebSocket):
        await websocket.accept()
        self.active_connections[job_id] = websocket

    def disconnect(self, job_id: str):
        self.active_connections.pop(job_id, None)

    async def send_update(self, job_id: str, message: dict):
        websocket = self.active_connections.get(job_id)
        if websocket:
            await websocket.send_json(message)

manager = ConnectionManager()
```

What you learn: why connections need to be managed (multiple users, multiple
jobs), why we key connections by job_id, what accept() does and when it must
be called, what happens if you try to send to a disconnected client.

### Step 3.3 — Add a WebSocket endpoint

Update `main.py`:

```python
from fastapi import WebSocket, WebSocketDisconnect
from connection_manager import manager

@app.websocket("/ws/{job_id}")
async def websocket_endpoint(websocket: WebSocket, job_id: str):
    await manager.connect(job_id, websocket)
    try:
        while True:
            await websocket.receive_text()  # keep connection alive
    except WebSocketDisconnect:
        manager.disconnect(job_id)
```

What you learn: why the endpoint loops forever (to keep the connection open),
what WebSocketDisconnect is and when it fires, why we catch it rather than
letting it crash the server.

How you know it works: open your browser console and run:
```javascript
const ws = new WebSocket("ws://localhost:8000/ws/test-job-id")
ws.onmessage = (e) => console.log(e.data)
```
The connection stays open.

### Step 3.4 — Broadcast from the worker via Redis pub/sub

This is the key architectural decision. The worker cannot directly access the
WebSocket connections because it is a separate process. It needs to communicate
through Redis.

Update `worker.py` to publish events:

```python
import redis as redis_sync
import json

redis_client = redis_sync.Redis(host="localhost", port=6379)

async def process_document(ctx, job_id: str, filename: str):
    db = SessionLocal()
    try:
        job = db.query(Job).filter(Job.id == job_id).first()
        job.status = "processing"
        db.commit()

        redis_client.publish(f"job:{job_id}", json.dumps({
            "job_id": job_id,
            "status": "processing"
        }))

        await asyncio.sleep(3)

        job.status = "completed"
        db.commit()

        redis_client.publish(f"job:{job_id}", json.dumps({
            "job_id": job_id,
            "status": "completed"
        }))

    finally:
        db.close()
```

Update `main.py` to subscribe to Redis and forward to WebSocket:

```python
import asyncio
import redis.asyncio as aioredis
import json
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    asyncio.create_task(redis_listener())
    yield

async def redis_listener():
    r = aioredis.Redis()
    pubsub = r.pubsub()
    await pubsub.psubscribe("job:*")
    async for message in pubsub.listen():
        if message["type"] == "pmessage":
            data = json.loads(message["data"])
            job_id = data["job_id"]
            await manager.send_update(job_id, data)

app = FastAPI(lifespan=lifespan)
```

What you learn: why pub/sub is needed (worker and API are separate processes),
what psubscribe does (subscribes to a pattern of channels), what a lifespan
context manager is in FastAPI and why it replaced the old startup event,
the difference between sync and async Redis clients.

How you know it works: open the browser WebSocket connection to a job ID,
submit that job, watch the status messages appear in the console in real time.

### Step 3.5 — Build the real-time frontend

In the Next.js frontend, create `app/components/JobCard.tsx`:

```typescript
"use client"
import { useEffect, useState } from "react"

interface JobCardProps {
  jobId: string
  filename: string
  initialStatus: string
}

export function JobCard({ jobId, filename, initialStatus }: JobCardProps) {
  const [status, setStatus] = useState(initialStatus)

  useEffect(() => {
    const ws = new WebSocket(`ws://localhost:8000/ws/${jobId}`)

    ws.onmessage = (event) => {
      const data = JSON.parse(event.data)
      setStatus(data.status)
    }

    ws.onclose = () => {
      console.log("WebSocket closed for job", jobId)
    }

    return () => ws.close()
  }, [jobId])

  return (
    <div className="border rounded p-4">
      <p className="font-medium">{filename}</p>
      <p className="text-sm text-gray-500">{status}</p>
    </div>
  )
}
```

What you learn: why the WebSocket connection goes in a useEffect (side effects
belong there), why we return ws.close() from the cleanup function (prevents
memory leaks and dangling connections), how useState updates the UI when the
WebSocket message arrives.

How you know it works: submit a job from the UI, watch the status on the card
change from queued to processing to completed without any page refresh.

## Phase 4 — Processing Stages (Days 14 to 17)

The queue and real-time updates work. Now we add the actual AI processing.
Replace the simulated sleep with real stages.

### Step 4.1 — Define the processing stages

Each stage is a separate function. They run sequentially. Each one updates
the job status and broadcasts a WebSocket event.

Create `backend/stages.py`:

```python
from groq import Groq
import os

client = Groq(api_key=os.getenv("GROQ_API_KEY"))

def extract_text(file_content: str) -> str:
    # For now just return the content
    # Later: add PDF extraction, OCR, Whisper
    return file_content

def classify_document(text: str) -> str:
    response = client.chat.completions.create(
        model="llama3-8b-8192",
        messages=[{
            "role": "user",
            "content": f"Classify this document into one of: invoice, contract, report, email, other. Reply with just the category.\n\n{text[:500]}"
        }]
    )
    return response.choices[0].message.content.strip()

def summarise_document(text: str) -> str:
    response = client.chat.completions.create(
        model="llama3-8b-8192",
        messages=[{
            "role": "user",
            "content": f"Summarise this document in 2-3 sentences.\n\n{text[:2000]}"
        }]
    )
    return response.choices[0].message.content.strip()

def extract_entities(text: str) -> list:
    response = client.chat.completions.create(
        model="llama3-8b-8192",
        messages=[{
            "role": "user",
            "content": f"Extract key entities (people, organisations, dates, amounts) from this text. Return as a JSON array of objects with 'type' and 'value' keys.\n\n{text[:2000]}"
        }]
    )
    import json
    try:
        return json.loads(response.choices[0].message.content)
    except:
        return []
```

What you learn: why stages are separate functions (single responsibility,
easier to test, easier to retry individual stages), why we truncate text
before sending to the LLM (context window limits and cost), why we wrap
the JSON parse in a try/except (LLMs do not always return valid JSON).

### Step 4.2 — Add a Stage model to PostgreSQL

Update `models.py`:

```python
class Stage(Base):
    __tablename__ = "stages"

    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    job_id = Column(UUID(as_uuid=True), ForeignKey("jobs.id"), nullable=False)
    name = Column(String, nullable=False)
    status = Column(String, default="pending")
    result = Column(String, nullable=True)
    started_at = Column(DateTime, nullable=True)
    completed_at = Column(DateTime, nullable=True)
```

Create an Alembic migration:
```bash
alembic revision --autogenerate -m "add stages table"
alembic upgrade head
```

What you learn: what a foreign key is and why it matters (enforces the
relationship between stages and jobs at the database level), what happens
if you try to create a stage for a job that does not exist (PostgreSQL
rejects it — data integrity).

### Step 4.3 — Update the worker to run stages

Update `worker.py` to run real stages and track them:

```python
from stages import extract_text, classify_document, summarise_document, extract_entities
from datetime import datetime

STAGES = [
    ("text_extraction", extract_text),
    ("classification", classify_document),
    ("summarisation", summarise_document),
    ("entity_extraction", extract_entities),
]

async def process_document(ctx, job_id: str, filename: str, content: str):
    db = SessionLocal()
    try:
        job = db.query(Job).filter(Job.id == job_id).first()
        job.status = "processing"
        db.commit()

        previous_result = content

        for stage_name, stage_fn in STAGES:
            stage = Stage(job_id=job_id, name=stage_name, status="running",
                         started_at=datetime.utcnow())
            db.add(stage)
            db.commit()

            redis_client.publish(f"job:{job_id}", json.dumps({
                "job_id": job_id,
                "stage": stage_name,
                "status": "running"
            }))

            try:
                result = stage_fn(previous_result)
                stage.status = "completed"
                stage.result = str(result)
                stage.completed_at = datetime.utcnow()
                previous_result = result
            except Exception as e:
                stage.status = "failed"
                db.commit()
                raise

            db.commit()

            redis_client.publish(f"job:{job_id}", json.dumps({
                "job_id": job_id,
                "stage": stage_name,
                "status": "completed",
                "result": str(result)[:200]
            }))

        job.status = "completed"
        db.commit()

    finally:
        db.close()
```

What you learn: why we pass the result of one stage as the input to the next
(pipeline pattern), why we commit after each stage rather than once at the end
(partial progress is saved if a later stage fails), why we publish to Redis
after both starting and completing each stage.

How you know it works: submit a document, watch five separate stage events
arrive on the WebSocket, check the stages table in PostgreSQL — five rows,
each with timing and results.

### Step 5.2 — Add a User model

```python
class User(Base):
    __tablename__ = "users"

    id = Column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    email = Column(String, unique=True, nullable=False)
```

### Step 5.3 — Implement password hashing and JWT

```
pip install python-jose[cryptography] passlib[bcrypt]
```

Create `backend/auth.py`:

```python
from jose import JWTError, jwt
from passlib.context import CryptContext
from datetime import datetime, timedelta
import os

SECRET_KEY = os.getenv("SECRET_KEY", "change-this-in-production")
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 60

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)

def create_access_token(user_id: str) -> str:
    expires = datetime.utcnow() + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES)
    return jwt.encode({"sub": user_id, "exp": expires}, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> str:
    payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
    return payload.get("sub")
```

What you learn: why we hash passwords and never store plain text, what bcrypt
does (adds a random salt, applies a slow hashing function — slow is intentional,
makes brute force attacks impractical), what the JWT secret key is for, what
the exp claim does, what HS256 means.

### Step 5.4 — Add register and login endpoints

```python
from auth import hash_password, verify_password, create_access_token

@app.post("/register")
def register(email: str, password: str, db: Session = Depends(get_db)):
    existing = db.query(User).filter(User.email == email).first()
    if existing:
        raise HTTPException(status_code=400, detail="Email already registered")
    user = User(email=email, hashed_password=hash_password(password))
    db.add(user)
    db.commit()
    return {"message": "registered"}

@app.post("/login")
def login(email: str, password: str, db: Session = Depends(get_db)):
    user = db.query(User).filter(User.email == email).first()
    if not user or not verify_password(password, user.hashed_password):
        raise HTTPException(status_code=401, detail="Invalid credentials")
    token = create_access_token(str(user.id))
    return {"access_token": token, "token_type": "bearer"}
```

### Step 6.2 — Define the agent tools

Create `agent/tools.py`:

```python
from langchain.tools import tool
import redis
import json
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
import os

DATABASE_URL = os.getenv("DATABASE_URL")
engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine)
redis_client = redis.Redis(host=os.getenv("REDIS_HOST", "localhost"))

@tool
def get_queue_depth() -> str:
    "Returns the current number of jobs waiting in the Redis queue."
    depth = redis_client.llen("arq:default")
    return f"There are currently {depth} jobs in the queue."

@tool
def get_failed_jobs() -> str:
    "Returns the number of failed jobs in the last hour and their IDs."
    db = SessionLocal()
    from models import Job, JobStatus
    from datetime import datetime, timedelta
    cutoff = datetime.utcnow() - timedelta(hours=1)
    failed = db.query(Job).filter(
        Job.status == JobStatus.failed,
        Job.updated_at > cutoff
    ).all()
    db.close()
    if not failed:
        return "No failed jobs in the last hour."
    ids = [str(j.id) for j in failed]
    return f"{len(failed)} failed jobs: {', '.join(ids)}"

@tool
def restart_job(job_id: str) -> str:
    "Restarts a failed job by re-enqueuing it."
    import asyncio
    from arq import create_pool
    from arq.connections import RedisSettings

    async def enqueue():
        db = SessionLocal()
        from models import Job, JobStatus
        job = db.query(Job).filter(Job.id == job_id).first()
        if not job:
            return f"Job {job_id} not found."
        job.status = JobStatus.queued
        db.commit()
        pool = await create_pool(RedisSettings())
        await pool.enqueue_job("process_document", job_id, job.filename, "")
        db.close()
        return f"Job {job_id} restarted."

    return asyncio.run(enqueue())
```

What you learn: what the @tool decorator does (makes the function available to
the agent with the docstring as the description the agent uses to decide when
to call it), why the docstring is critical (the agent reads it to understand
what the tool does), why tools return strings (the agent reads the output and
reasons about it).

### Step 6.3 — Create the agent

Create `agent/main.py`:

```python
from langchain_groq import ChatGroq
from langchain.agents import create_react_agent, AgentExecutor
from langchain import hub
from tools import get_queue_depth, get_failed_jobs, restart_job
import time
import os

llm = ChatGroq(model="llama3-8b-8192", api_key=os.getenv("GROQ_API_KEY"))
tools = [get_queue_depth, get_failed_jobs, restart_job]
prompt = hub.pull("hwchase17/react")

agent = create_react_agent(llm, tools, prompt)
executor = AgentExecutor(agent=agent, tools=tools, verbose=True, max_iterations=5)

def check_pipeline_health():
    result = executor.invoke({
        "input": (
            "You are a pipeline monitoring agent. Check the current queue depth and "
            "look for any failed jobs in the last hour. If there are failed jobs, "
            "restart them. Report what you found and what actions you took."
        )
    })
    print(result["output"])

if __name__ == "__main__":
    print("Agent starting. Checking every 60 seconds.")
    while True:
        check_pipeline_health()
        time.sleep(60)
```

What you learn: what create_react_agent does, what AgentExecutor does, why
max_iterations matters (prevents infinite loops if the agent gets confused),
what verbose=True shows you (the full reasoning trace — essential for
understanding and debugging agents).

How you know it works: run the agent. Intentionally fail a few jobs. Watch
the agent detect them and restart them. Read the verbose output — understand
every reasoning step.
